To independently re-execute the entire FastAPI application, LangGraph orchestration, SQLite checkpointer, retrieval index, fixture tools, guardrails, deterministic checks, metrics and regression gate offline with zero API calls:

```bash
python -m eval.run --replay eval/reports/openai/cassette.json.gz --out /tmp/replayed
python -m eval.compare eval/reports/openai/report.json /tmp/replayed.json
```

Expected output:

```text
REPRODUCED: 408 answers and every metric compared (0 differences)
```

`eval.compare` verifies every answer's SHA-256 across all 3 repeats of all 136 conversations, every metric across all five suites, the exact regression gate verdict, and that `unused_recorded_calls == 0`. Unrecorded requests raise `CassetteMiss` loudly. GitHub Actions runs this exact check automatically on every push and pull request in the `model-eval-replay` job ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)). The recording was made with 4 golden conversations in flight; each records under its own cassette scope, so the replay is exact whatever order the threads ran in ([ADR-0025](docs/adr/0025-parallel-golden-conversations-and-fail-fast.md)); it takes about 1.5 minutes offline.

## Answers to the Five Interview Questions

### 1. Quality gate (primary question)
> *Your own regression gate failed at 0.833 against a 0.94 floor. Would you lower the threshold, change the system, or change the dataset? What evidence would you require before making that decision?*

**Change the system first; never lower a floor after seeing a failure, and never soften a sealed split.**

In v3 we separated three distinct sources of error before touching anything:
1. **Real system defects** (7 of 13 failures on 2026-11-16: `g01`, `g12`, `g15`, `h14`, `s04`, `s21`×2): fix the system (output guard, hosted dense + multi-query retrieval, Critic `evidence_checklist`, prompt refinements) and re-seal a brand-new held-out split (`sealed-2` → `sealed-3` → `sealed-4`) after every `src/` change so we never grade fixes on the items that inspired them.
2. **Gate aggregation rule vs threshold** ([ADR-0019](docs/adr/0019-gate-over-repeated-runs.md)): with `n=18`, one item is `0.056`, so gating only Run 1 made the pass/fail verdict depend on run order. Before measuring v3, we changed the gate to read **all `N` runs** (mean ≥ floor, no single run > 1 item below, ceilings must hold on every run) while leaving `dev >= 0.94` untouched. That rule is strictly *harder* to pass on a lucky Run 1, and still fails the 2026-11-16 report (`0.870 < 0.94`).
3. **Grader error vs system error**: on `dev`/`validation`, broken regexes (`s07` matching a negation, `g07` missing `€`) and stale references (`s69` dummy `SO-00000001`) are legitimate dataset fixes *once the split is no longer sealed*. On `sealed-4`, every regex miss (`s76`, `s79`, `s85`, `s93`) stays untouched and is reported raw (`0.903`) next to adjudicated (`1.000`).

**Evidence required before ever revisiting a floor:** a clean, multi-run measurement (`--repeat 3`, zero degraded turns) plus per-item SHA-256 adjudication showing whether misses come from the agent or from judge variance. That evidence is what we acted on. The first cassette run on the `479a6d7` freeze ([`44569607884`](https://github.com/DanielQueijeiro/AI_Hardcore/actions/runs/44569607884)) passed every gate but `dev` (`0.889, 0.833, 0.944`). Adjudication split its six `dev` misses into three real agent omissions (`g08` half a decline code, `g17` settlement amounts dropped, `g01` shared card rates dropped) and three judge marks against unrequested extras (`g13`×2, `g15`). We changed the system for both: deterministic checklist items for the omissions, and prompt rules that keep answers to what was asked so the judge has nothing extra to mark down ([ADR-0026](docs/adr/0026-dev-driven-fixes-after-the-479a6d7-freeze.md)), all from `dev` evidence, with `sealed-4` never opened. Local real-model checks of `dev` (18 runs) settled at `0.963` before the final CI run [`44622842628`](https://github.com/DanielQueijeiro/AI_Hardcore/actions/runs/44622842628), which scored **`dev` `1.000` on all three runs** and passed every gate with the `0.94` floor untouched.

### 2. Critic
> *Your Critic missed real omissions such as the Wi-Fi step. How would you improve completeness checking without turning the Critic into another generator subject to the same errors?*

**Move structural extraction into deterministic code, and let the LLM Critic verify against an explicit checklist instead of re-reading raw prose from scratch.**

In v3 (`src/agents/checks.py`), `evidence_checklist(question, evidence, draft)` deterministically parses the turn's collected evidence into three concrete lists before the Critic runs:
- **Procedure steps** from matching runbook/FAQ sections (scoped to sections whose heading/code matches the turn's telemetry or question — a bug we caught after CI run 1 when a shared `internal://support-runbook` URL bled offline steps onto decline turns);
- **Product prices / rental figures** when a product comparison or pricing question retrieved multiple machines;
- **Human-operator decisions** (`APPROVED`, `REJECTED`, `ANSWERED`, `TIMED_OUT`) and service-order numbers when HITL ran.

The Critic still evaluates semantics (is the step actually covered, was a rejection stated plainly, was a caveat included), so it never degenerates into brittle regex matching — yet it no longer has to notice a missing step by free-form rereading. We then validated the Critic on **48 fixed drafts** (`32` dev + `16` blind unseen `heldout` `k33`–`k48`) covering 8 defect classes: recall rose to **`1.000` (24/24 overall, 8/8 held-out)** with **`0.000` false revise on held-out**, without adding an extra generator pass. The trade-off is visible too: the checklist items added in `e031a8e` raised false revise on the older clean `dev` drafts from `0.042` to `0.167` (4/24, under the `0.20` ceiling), because a stricter checklist also sends back some drafts that were acceptable before; we report it rather than relabel those drafts after the fact.

### 3. Retrieval
> *`s04` failed because the query was reformulated in Portuguese against an English corpus. How would you redesign multilingual retrieval without relying on a glossary developed alongside the evaluation set?*

**Replace lexical-only dependence with multilingual dense embeddings plus multi-query fan-out, and prove it with a post-glossary held-out split and a `glossary_off` ablation.**

Specifically ([ADR-0020](docs/adr/0020-retrieval-mode-from-a-held-out-split.md)):
1. **Multilingual dense embeddings as the primary ranker when a key is available (`RETRIEVAL_MODE=auto`, `EMBEDDING_PROVIDER=auto` → `text-embedding-3-small`)**, degrading automatically to BM25 on embedding API error so an outage never fails a tool call.
2. **Multi-query retrieval** (`search_getnet_knowledge(query, query_en)` + the merchant's raw message, batched via `search_many()` and fused with RRF), so an agent searching in Portuguese never blinds retrieval to English passages or vice versa.
3. **Empirically tested without the glossary** on 36 new colloquial EN/PT/ES queries (`rh01`–`rh36`) written after the glossary was frozen:
   - Keyless BM25 collapsed from `0.988` dev to **`0.708` Recall@4 / `0.632` MRR** (Spanish `0.375`), confirming glossary optimism.
   - Hosted dense reached **`1.000` Recall@4 (36/36) / `0.944` MRR** on held-out — **identical with `glossary_off` (`1.000 / 0.944`)**, and stronger than hosted hybrid (`0.917 / 0.810`), where weak BM25 rankings diluted dense hits.
   - `s04` now passes `3/3`.

### 4. Agentic cost
> *A turn currently uses roughly five to nine sequential model calls. Where would you parallelize or eliminate calls without weakening bounded autonomy, groundedness or security?*

We applied two latency optimizations in v3 without touching any security boundary or autonomy bound:
1. **Speculative Router step 1 overlapped with the LLM input guardrail (`SPECULATIVE_ROUTER=true`, `src/agents/nodes.py`):** The deterministic input guard still runs synchronously first (zero-latency block). Only if it passes do the LLM input classifier and Router step 1 execute concurrently. If the classifier blocks, the speculative Router output is discarded cleanly — no tool executes before the classifier allows the turn, so security and structural isolation are completely untouched.
2. **Parallel fan-out of independent subtasks (`delegate_parallel`, capped at `MAX_PARALLEL_TASKS=3`):** Compound queries ("what is my settlement schedule AND what are Crediário's terms?") dispatch Knowledge and Support concurrently instead of serializing two Router→Specialist round-trips. Each branch keeps its own tool allow-list, principal scope, and tool-step cap (`4`). Prompts explicitly forbid `delegate_parallel` when one branch depends on another's lookup (e.g., "look up my terminal model, then check fees for that model", added after `s63`).

**What we deliberately did *not* cut:** the Critic (removing it drops groundedness/completeness safety on high-stakes billing/HITL answers) and the structural tool/HITL boundaries. Next step beyond v3 if latency must drop below 5 s p50: run a faster non-reasoning model for the input classifier and specialist tool-routing calls, keeping the stronger model for Router synthesis and the Critic, and pre-cache embeddings for common queries.

### 5. Judge validity
> *You achieved κ=1.0 on the calibration set but found a real judge error in the report. How would you design calibration that better measures borderline cases?*

A calibration set of clear-cut good vs bad answers only proves the judge is awake — it cannot measure the failure mode that actually hurts real evals: **borderline omissions, subtle ungrounded additions, hedged answers, and long-evidence groundedness errors.**

In v3 we built [`eval/datasets/judge_borderline.jsonl`](eval/datasets/judge_borderline.jsonl) (**20 near-miss items**, paired across subtle omissions like the Wi-Fi step `b04b`, hedged answers `b03b`, minor ungrounded additions `b07a`, wrong caveats, and partial answers) labelled independently by two blind reviewers before running `gpt-5.4-mini` on them ([`eval/labels/README.md`](eval/labels/README.md)):
- **Reviewer 1** (independent cross-family Gemini pass, blind to Reviewer 2 and to the OpenAI judge) and **Reviewer 2** (human, Daniel Queijeiro) agreed **20/20 (`1.000`, κ `1.000`)** against the rubric sheet.
- **Locked floor before running the judge:** `calibration.by_set.borderline.agreement >= 0.75`.
- **Measured result ([`44622842628`](https://github.com/DanielQueijeiro/AI_Hardcore/actions/runs/44622842628)):** while `original` (16/16) and `independent` (24/24) stayed at **`1.000` (κ `1.000`)**, `borderline` dropped to **`0.850` agreement (17/20, κ `0.700`, 3 false passes, 0 false fails)** — catching the exact failure mode (`b04b` passed an answer that omitted the Wi-Fi step, `b03b` passed a hedged answer, `b07a` passed an ungrounded extra detail).

And our adjudications expose the complementary judge failure mode in production traces: **false fails on correct answers that carry a caveat or extra grounded detail** (10 of 23 raw failures in [`44569607884`](https://github.com/DanielQueijeiro/AI_Hardcore/actions/runs/44569607884), 3 of 17 in the final run: `h18`, `s18`, `s43`). In the final run the larger grader error is the deterministic fact patterns (12 of 17), which we leave untouched on the sealed split and report raw (`sealed-4` `0.875`) next to adjudicated (`1.000`). The honest conclusion — backed by both `borderline` calibration and `--regrade` / SHA-256 adjudication — is that a single-call mini judge has a ~2–3% noise floor; the next calibration & harness step is (a) two external human annotators on borderline cases (ours is 1 human + 1 cross-family model, stated plainly in `eval/labels/README.md`) and (b) evidence-snippet scoping or majority-of-3 judging on high-stakes gates.
